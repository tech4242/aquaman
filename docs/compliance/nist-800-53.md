# NIST SP 800-53 Rev 5 Mapping

aquaman maps to **NIST SP 800-53 Rev 5** control families that govern authentication, access enforcement, key management, and audit. Same evidence applies to **NIST CSF 2.0** (`PR.AA-*`, `DE.AE-*`) and **SOC 2 Common Criteria** (CC6.1 logical access, CC6.6 transmission, CC7.2 system monitoring).

| Control ID | Family | aquaman feature | Test |
|---|---|---|---|
| **IA-5** | Authenticator Management | Eight vault backend implementations (Keychain, 1Password, HashiCorp Vault, KeePassXC, encrypted-file, systemd-creds, Bitwarden, Keeper). Credentials are stored, rotated, and accessed via the vault's native APIs. With the `encrypted-file` backend the vault is aquaman's own file, encrypted with AES-256-GCM under a password-derived key ([BSI TR-02102-1 mapping](bsi-tr-02102.md)). | [`test/compliance/nist/ia-5-authenticator-mgmt.test.ts`](../../test/compliance/nist/ia-5-authenticator-mgmt.test.ts) |
| **AC-3** | Access Enforcement | Per-service request-policy engine evaluates method + path against allow/deny rules *before* credentials are injected. | **AU-9** | Protection of Audit Information | Each entry carries a sequence number and the hash of the entry before it, and its own hash covers both (SHA-256). It then compares the log with its anchor: the sequence and hash of the last entry and the sequence the log is supposed to begin at (`from`), which a process that writes the log stores in the credential store at most once every `audit.anchorIntervalSeconds` (default 60, or 900 with 1Password, Bitwarden or Keeper; `0` turns it off), at once after it pruned old archives, and at graceful shutdown. A log that ends before the anchored sequence, is empty or missing, holds a different entry there, or begins later than `from` fails, so a truncated, emptied, deleted or rebuilt log is detected, and so is one whose early entries were removed: only pruning raises `from`. Several processes may write one log (a daemon and a proxy OpenClaw started); each append is made under a lock file and continues from what is on disk, so they form one chain. Commands that read the log (`audit verify`, `audit tail`) never change it. The limits, each a failing-by-design row in the test: entries written after the last anchor are not anchored, so cutting off the entries of the last interval is not detected; software that can write to the credential store can move or delete the anchor, or raise its `from`, as well as change the log; an anchor written without `from` says nothing about where the log begins. The anchor is not reachable through aquaman by a caller: the broker, the proxy, the OpenShell driver, `aquaman credentials` and the migration from an OpenClaw config refuse the reserved service name. A log with no anchor yet (written before anchoring existed, or by a process that has not stored one) passes as "not anchored yet". If the credential store cannot be read, `audit verify` fails and says so; `--chain-only` checks the chain alone. `aquaman audit accept` sets the anchor to the log as it is, for a log that was restored or deleted on purpose; it needs a terminal, a typed yes and no proxy running, and writes an entry recording the reset. The log is `0600` in a `0700` directory. See [The audit log's anchor](#the-audit-logs-anchor). | [`au-9-au-10-tampering.test.ts`](../../test/compliance/nist/au-9-au-10-tampering.test.ts): one row per attack; the undetected ones are `it.fails` rows. [`audit-anchor-reserved.test.ts`](../../test/compliance/audit-anchor-reserved.test.ts): the reserved name at every entry point. [`audit-log-shared.test.ts`](../../test/unit/audit-log-shared.test.ts) and [`audit-log-processes.test.ts`](../../test/e2e/audit-log-processes.test.ts): several writers and a reader on one log |

## The audit log's anchor

The hash chain is unkeyed and lives in one directory. On its own it shows a change inside the log and nothing else: a log with its end cut off, an empty log and a log rebuilt from scratch are each a valid chain. The anchor is the part kept somewhere else.

- **What it is.** `{ "v": 1, "seq": <n>, "hash": "<hash of entry n>", "at": "<time>", "from": <m> }`, stored in the configured credential backend as `aquaman_internal/audit_anchor`. `seq` and `hash` say where the log ended. `from` is the lowest sequence that is supposed to be on disk: 1 until old archives are pruned (`maxArchives`, ten by default), then the first entry of the oldest archive that was kept. Pruning is the only thing that raises it, and it never goes down.
- **Who writes it.** A process that writes the log while it serves: `aquaman daemon`, and the proxies OpenClaw starts. After an entry is written it stores a new anchor at most once per `audit.anchorIntervalSeconds`, at once after it pruned (until the anchor says so, the log looks as if it had lost its early entries), and once more when it is stopped with SIGINT or SIGTERM. At shutdown it waits five seconds at most for the vault; if the vault does not answer it prints `AUDIT FAILURE: ...` and exits. An idle process writes nothing.
- **Several processes, one log.** A daemon and a proxy OpenClaw started on the same config directory both write the log. Each append is made under a lock file in the audit directory (`write.lock`, held for one append) and continues from the last entry on disk, so the two form one chain with consecutive sequence numbers. A writer that cannot get the lock within two seconds fails that write, and the request it belongs to is answered as any request whose audit entry could not be written (`audit_unavailable`); a lock left by a process that is gone, or older than five seconds, is taken over. Each process reads the anchor in the vault before it writes its own and leaves it alone when it is not behind. A writer follows only entries that link to the last one it wrote: if the log was cut short or replaced under a running process, that process goes on from its own entry, prints `AUDIT FAILURE: ...`, and the chain shows the break.
- **Reading never changes the log.** `aquaman audit verify` and `aquaman audit tail` create no file or directory and do not touch the write-ahead file, so they can run beside a serving proxy. When the files change while `audit verify` reads them, it reads again before it reports an error. The default is 60 seconds. With 1Password, Bitwarden or Keeper each write runs that vault's CLI, which can ask you to unlock it, so the default there is 900 seconds; with `encrypted-file` or KeePassXC a write rewrites the file. That is why writes are spaced out and not made per request. `anchorIntervalSeconds: 0` turns anchoring off.
- **It only moves forward.** At start the process compares the log with the stored anchor. If the log is behind it, holds a different entry at that sequence, or begins later than `from`, it prints `AUDIT FAILURE: ...` on stderr, keeps serving and logging, and writes no anchor until a person has run `aquaman audit accept`. A failed anchor write is also an `AUDIT FAILURE` line and is tried again at the next interval; it never fails a request.
- **`aquaman audit verify`** exits 0 when the chain is valid, the log holds the anchored entry and begins no later than `from`, and prints how many entries follow the anchor. It exits 1 when the log is truncated, missing or rebuilt, when entries are missing from its beginning (`head_missing`: "entries N to M are missing: they were on disk when the anchor was written"), when the stored value is not an anchor, and when the credential store cannot be read. `--chain-only` skips the anchor and says that it did. `--json` prints `valid`, `chain` (`valid`, `errors`, `entries`, `last_seq`, `last_hash`, `verified_from`), `anchor` (`status`, `seq`, `at`, `from`, `unanchored`, `message`) and `fix`.
- **The bootstrap case.** A log with no anchor in the credential store passes and is reported as "not anchored yet". That is a log written before anchoring existed, or one whose process has not stored an anchor. Entries written without a sequence number count by their line position, and the next entry written continues from there.
- **`aquaman audit accept`** is for a log that legitimately differs from its anchor: restored from a backup, or deleted on purpose. It asks for a typed `yes` at a terminal and refuses without one, refuses while a proxy is running, writes an entry that records the old and new sequence, and sets the anchor to the log as it is, with `from` at the first entry that is on disk. It does not accept a log whose chain is broken; move the audit directory aside first so a new log starts.

What it does not cover:

- Entries written after the last anchor are not anchored. Cutting off the newest entries, up to one interval's worth, is not detected.
- Software that can write to the credential store can move or delete the anchor. The anchor is as well protected as the vault is: a vault that asks before each write, or one that other software running as you cannot open, protects it; the `encrypted-file` backend with its password in the environment of that software does not.
- Software that can write to the credential store can also raise `from`, and then remove the entries before it.
- An anchor written without `from` says nothing about where the log begins. No release wrote one. `audit verify` passes such a log and says that it was not checked for missing early entries; the next anchor a serving process writes carries `from`, taken from the log as it is then.
- Pruning deletes the old archives before the anchor can say so. A process that is killed in between, or whose vault cannot be written then, leaves a log that begins later than its anchor says. `audit verify` reports the pruned entries as missing, a process that starts on that log pauses anchoring, and `aquaman audit accept` is the way forward. Nothing was tampered with, and nothing in the log can show that.
- A writer follows the log from the file that holds its own last entry. If other processes rotate and prune that file away between two writes of one process (ten rotations, 100 MB, with the defaults), that process cannot tell the log from a replaced one, goes on from its own entry, and the chain is broken from there.
- Two processes that find the same lock abandoned in the same instant can both take it, and then write the same sequence number. That needs a writer that stopped in the middle of an append and two others waiting for it. It is not covered by a test.
- If the process is killed and the archive holding the anchored entry is pruned before it starts again, the log can no longer be tied to its anchor. It is reported, and `aquaman audit accept` is the way forward.

## What this is not

- Not an audit certification (SOC 2 / ISO 27001 / FedRAMP / etc.). Those require a third-party assessor.
- Not a complete control implementation — aquaman is a *component* that contributes evidence to those controls. The end-to-end control evaluation depends on how the operator deploys aquaman (vault backend choice, policy config, OS-level access to `~/.aquaman/`, etc.).
- The `aquaman-hermes` Python plugin contributes evidence only as a credential-free status/health layer. It enforces no control itself; the loopback isolation is proxy-side. Its conformance tests assert it does not *undermine* the proxy's guarantees (no credential held, harvested, or logged), not that it implements them.
- The daemon's credential cache (v0.13.1+) keeps vault-fetched values in proxy memory for a bounded TTL (default 15 min for 1Password/Bitwarden/Vault, else off; `cacheTtlSeconds: 0` disables). It is memory-only (SC-28 unaffected), sits behind policy enforcement (AC-3), emits audit events per request rather than per backend fetch (AU-2), and write-invalidates so vault rotation via aquaman is immediate (IA-5). Conformance: [`test/compliance/cache-residency.test.ts`](../../test/compliance/cache-residency.test.ts).
