# NIST SP 800-53 Rev 5 Mapping

aquaman maps to **NIST SP 800-53 Rev 5** control families that govern authentication, access enforcement, key management, and audit. Same evidence applies to **NIST CSF 2.0** (`PR.AA-*`, `DE.AE-*`) and **SOC 2 Common Criteria** (CC6.1 logical access, CC6.6 transmission, CC7.2 system monitoring).

|---|---|---|---|
| **IA-5** | Authenticator Management | Eight vault backend implementations (Keychain, 1Password, HashiCorp Vault, KeePassXC, encrypted-file, systemd-creds, Bitwarden, Keeper). Credentials are stored, rotated, and accessed via the vault's native APIs. With the `encrypted-file` backend the vault is aquaman's own file, encrypted with AES-256-GCM under a password-derived key ([BSI TR-02102-1 mapping](bsi-tr-02102.md)). | [`test/compliance/nist/ia-5-authenticator-mgmt.test.ts`](../../test/compliance/nist/ia-5-authenticator-mgmt.test.ts) |

| **AU-9** | Protection of Audit Information | Each entry carries a sequence number and the hash of the entry before it, and its own hash covers both (SHA-256). It then compares the log with its anchor: the sequence and hash of the last entry, which the process that writes the log stores in the credential store at most once every `audit.anchorIntervalSeconds` (default 60, `0` turns it off) and at graceful shutdown. A log that ends before the anchored sequence, is empty or missing, or holds a different entry there fails, so a truncated, emptied, deleted or rebuilt log is detected. The limits, each a failing-by-design row in the test: entries written after the last anchor are not anchored, so cutting off the entries of the last interval is not detected; software that can write to the credential store can move or delete the anchor as well as the log; an old archive that was deleted looks the same as one that was pruned (the result says which sequence the log was verified from). The anchor is not reachable through aquaman by a caller: the broker, the proxy, the OpenShell driver and `aquaman credentials` refuse the reserved service name. A log with no anchor yet (written before anchoring existed, or by a process that has not stored one) passes as "not anchored yet". If the credential store cannot be read, `audit verify` fails and says so; `--chain-only` checks the chain alone. `aquaman audit accept` sets the anchor to the log as it is, for a log that was restored or deleted on purpose; it needs a terminal, a typed yes and no proxy running, and writes an entry recording the reset. The log is `0600` in a `0700` directory. See [The audit log's anchor](#the-audit-logs-anchor). | [`au-9-au-10-tampering.test.ts`](../../test/compliance/nist/au-9-au-10-tampering.test.ts): one row per attack; the undetected ones are `it.fails` rows. [`audit-anchor-reserved.test.ts`](../../test/compliance/audit-anchor-reserved.test.ts): the reserved name at every entry point |

## The audit log's anchor

The hash chain is unkeyed and lives in one directory. On its own it shows a change inside the log and nothing else: a log with its end cut off, an empty log and a log rebuilt from scratch are each a valid chain. The anchor is the part kept somewhere else.

- **What it is.** `{ "v": 1, "seq": <n>, "hash": "<hash of entry n>", "at": "<time>" }`, stored in the configured credential backend as `aquaman_internal/audit_anchor`.
- **Who writes it.** The process that writes the log while it serves: `aquaman daemon`, and the proxies OpenClaw starts. After an entry is written it stores a new anchor at most once per `audit.anchorIntervalSeconds` (default 60) and once more when it is stopped with SIGINT or SIGTERM. An idle process writes nothing. With 1Password, Bitwarden or Keeper each write runs that vault's CLI, and with `encrypted-file` or KeePassXC it rewrites the file, which is why writes are spaced out and not made per request. `anchorIntervalSeconds: 0` turns anchoring off.
- **It only moves forward.** At start the process compares the log with the stored anchor. If the log is behind it or holds a different entry at that sequence, it prints `AUDIT FAILURE: ...` on stderr, keeps serving and logging, and writes no anchor until a person has run `aquaman audit accept`. A failed anchor write is also an `AUDIT FAILURE` line and is tried again at the next interval; it never fails a request.
- **`aquaman audit verify`** exits 0 when the chain is valid and the log holds the anchored entry, and prints how many entries follow the anchor. It exits 1 when the log is truncated, missing or rebuilt, when the stored value is not an anchor, and when the credential store cannot be read. `--chain-only` skips the anchor and says that it did. `--json` prints `valid`, `chain` (`valid`, `errors`, `entries`, `last_seq`, `last_hash`, `verified_from`), `anchor` (`status`, `seq`, `at`, `unanchored`, `message`) and `fix`.
- **The bootstrap case.** A log with no anchor in the credential store passes and is reported as "not anchored yet". That is a log written before anchoring existed, or one whose process has not stored an anchor. Entries written without a sequence number count by their line position, and the next entry written continues from there.
- **`aquaman audit accept`** is for a log that legitimately differs from its anchor: restored from a backup, or deleted on purpose. It asks for a typed `yes` at a terminal and refuses without one, refuses while a proxy is running, writes an entry that records the old and new sequence, and sets the anchor to the log as it is. It does not accept a log whose chain is broken; move the audit directory aside first so a new log starts.

What it does not cover:

- Entries written after the last anchor are not anchored. Cutting off the newest entries, up to one interval's worth, is not detected.
- Software that can write to the credential store can move or delete the anchor. The anchor is as well protected as the vault is: a vault that asks before each write, or one that other software running as you cannot open, protects it; the `encrypted-file` backend with its password in the environment of that software does not.
- Archives are pruned from the old end, so a deleted old archive is indistinguishable from a pruned one. `audit verify` reports the sequence it verified from.
- If the process is killed and the archive holding the anchored entry is pruned before it starts again, the log can no longer be tied to its anchor. It is reported, and `aquaman audit accept` is the way forward.

## SOC 2 Common Criteria mapping

| SOC 2 CC | NIST equivalent | Same evidence applies |
|---|---|---|
| **CC6.1** Logical access — restrict access to information assets | IA-5, AC-3, AC-6 | Yes |
| **CC6.6** Transmission of sensitive information | SC-12, SC-28 (in-transit covered by UDS + chmod 0o600 + operator-chosen TLS to upstream) | Yes |
| **CC7.2** Monitor system for unauthorized activity | AU-2, AU-9, AU-10 | Yes |

## What this is not

- Not an audit certification (SOC 2 / ISO 27001 / FedRAMP / etc.). Those require a third-party assessor.
- Not a complete control implementation — aquaman is a *component* that contributes evidence to those controls. The end-to-end control evaluation depends on how the operator deploys aquaman (vault backend choice, policy config, OS-level access to `~/.aquaman/`, etc.).
- The `aquaman-hermes` Python plugin contributes evidence only as a credential-free status/health layer. It enforces no control itself; the loopback isolation is proxy-side. Its conformance tests assert it does not *undermine* the proxy's guarantees (no credential held, harvested, or logged), not that it implements them.
- The daemon's credential cache (v0.13.1+) keeps vault-fetched values in proxy memory for a bounded TTL (default 15 min for 1Password/Bitwarden/Vault, else off; `cacheTtlSeconds: 0` disables). It is memory-only (SC-28 unaffected), sits behind policy enforcement (AC-3), emits audit events per request rather than per backend fetch (AU-2), and write-invalidates so vault rotation via aquaman is immediate (IA-5). Conformance: [`test/compliance/cache-residency.test.ts`](../../test/compliance/cache-residency.test.ts).
